## 一、一句话

一个镜像同时支持 A / B / C 三题：平台给哪一题的数据，镜像按输入结构自动判题、自动选检查点与指标口径。
**三个提交位都上传同一个 tar**，不需要为每题单独打包。

## 三、判题规则（为什么一个镜像能跑三题）

判据是 `inputs` 的**结构**，三题天然不同，不存在歧义：

| 题 | 输入结构 | 判定 | 任务 | 主指标 |
|---|---|---|---|---|
| A | `inputs.features` 是长度 128 的数组 | 气体六分类 | classification | Macro-F1 ↑ |
| B | `inputs.features` 是 `{horizontal, vertical}` 两通道 | 轴承 RUL（分钟） | regression | RMSE ↓ |
| C | `inputs.settings`(3) + `inputs.sensors`(21) | C-MAPSS RUL（循环） | regression | RMSE ↓ |

启动日志第一行会打出判定结果，可直接核对：

```
[harness] route {"profile": "C", "source": "probe", "data_dir": "/data",
                 "input_mode": "abs8", "target_power": "1.0"}
```

`profile` 就是这次跑的题。若平台没挂数据（回退到镜像自带的 B 数据），`source` 会是 `bundled` 而不是 `probe`。

## 五、两处必须能解释的细节

**1. A 题第 6 轮与第 5 轮配置相同，结果也相同（0.7252）。**
这是有意的：候选表用尽后停在最后一条，用来验证「同配置从同一起点重跑，结果逐位可复现」。两次都是 0.7252，说明训练是确定的。

**2. C 题第 3 轮 51.1378 比当前最好 51.2684 更好，却被回滚。**
因为改善只有 0.25%，低于 0.5% 的采纳门槛。2.3 万条验证样本上 0.25% 约等于 0.13 个 RMSE 单位，与重复运行的波动同量级，不足以判定为真实提升。这是规则设计，不是漏判——如果要"能涨就收"，把 `MIN_GAIN` 调到 0.002 即可，但那会让门控失去意义。

## 六、B 题的 302.75 为什么必须用这个镜像复现

同一份代码、同一份数据、同一个起点，在 **linux/amd64 容器内**稳定给出 302.75（0.5 / 0.6 / 0.7 / 0.8 / 0.9 五个版本、累计 6 次实跑，逐位相同）；
在 **Windows 原生 Python** 下给出 315.92，差 4.3%。

原因是训练 105 个 epoch，每步的矩阵乘法由 OpenBLAS 完成，Windows 与 musl/glibc 的归约顺序不同，浮点差异在 105 个 epoch 上被逐步放大。**所以本地 Windows 只用于功能验证，所有对外声明的数值一律以容器内实测为准。**

这条不是免责声明，而是可验证的：`_verify08/console.log`（0.8 复核）与 `runs_tri_v09/b/console.log`（0.9 复跑）都记录着 `rmse 302.75`。

## 七、平台操作（三个提交位）

1. 在**任一题**的镜像上传入口，上传 `zxj-harness-0.9.tar`；
2. 等状态变成「就绪」，对这条镜像点「用于新版本」；
3. 三个提交位（A/B/C）分别建版本，**都选这条镜像**；
4. 每个版本单独跑试运行。三次运行的日志会各自打出 `route`，`profile` 分别是 A / B / C — 这是判断「这一位跑的是不是它该跑的那题」的唯一可靠依据。

若某个提交位的 `route` 显示 `profile` 与题目不符，说明平台把数据挂到了镜像自带的 `public/`（B 的数据），此时日志里 `data_source` 会是 `bundled`，需要向主办方确认数据挂载路径。
